# RomanBench pilot runbook

This runbook covers the first real RomanBench annotation pilot using the GitHub Pages annotator plus the Google Sheets / Apps Script backend.

## What annotators receive

Every annotator gets a **personal GitHub Pages URL** generated by `createAnnotator()`.

Pattern:

```text
https://vishwanath-gowda.github.io/KannadaLLMBench/?annotator=KN001&token=<UNIQUE_TOKEN>&batch=pilot-v1
```

Do **not** send only the base site URL. The backend requires all three query parameters:

- `annotator`: pseudonymous annotator ID;
- `token`: unique bearer token for that annotator;
- `batch`: annotation batch, for example `pilot-v1`.

Create one link per person in Apps Script:

```javascript
createAnnotator(
  'KN002',
  'https://vishwanath-gowda.github.io/KannadaLLMBench',
  'pilot-v1'
)
```

The function prints the full personal URL in the Apps Script execution log. Send that URL only to the intended contributor. Anyone holding the URL can submit as that pseudonymous annotator, so treat it like a password.

If a link is exposed, rerun `createAnnotator()` for the same ID. This rotates the token and invalidates the old link.

## Pilot annotation protocol

Annotators see a Kannada sentence and one Roman/Latin-script candidate.

Question 1:

> Does the Roman text have the same meaning as the Kannada sentence?

If the answer is **No**, the item is submitted immediately. Question 2 is not shown because typing plausibility is undefined when the Roman text does not preserve the meaning.

If the answer is **Yes**, Question 2 appears:

> Would you type Kannada this way using English letters?

Question 2 is specifically about Roman-letter spelling / typing plausibility. It is **not** a judgment of whether the underlying Kannada is formal, colloquial, dialectal, or code-mixed.

Stored interpretation:

```text
Meaning = No  -> typing label = N/A / blank
Meaning = Yes -> typing label = Yes or No
Skip          -> both labels blank
```

## First pilot design

Use approximately **30 semantic families**.

For this first process-calibration pilot:

- one Roman candidate per semantic family;
- `target_votes = 2`;
- 4–5 independent Kannada-speaking annotators;
- no annotator sees more than one Roman variant from the same semantic family;
- annotators do not see other annotators' decisions;
- the pilot mixes controlled Romanization styles so both accepted and rejected typing forms can occur;
- synthetic/public-corpus-derived pilot items are process-calibration material, not automatically benchmark gold.

Thirty tasks with two votes require 60 completed judgments. With five annotators, a balanced target is about 12 completed items per person. With four annotators, about 15 per person.

## Build the pilot task CSV

First construct a candidate pool. A small pool is sufficient for the pilot:

```bash
make romanbench-candidates \
  FAMILIES=100 \
  ROMAN_OUTPUT=data/interim/romanbench/pilot-candidates.jsonl
```

Then select one candidate from 30 semantic families and generate the exact Google Sheet `Tasks` schema:

```bash
make romanbench-pilot \
  PILOT_INPUT=data/interim/romanbench/pilot-candidates.jsonl \
  PILOT_OUTPUT=data/interim/romanbench/pilot-v1-tasks.csv \
  PILOT_FAMILIES=30 \
  PILOT_BATCH=pilot-v1
```

The selector is deterministic for a fixed seed. It attempts to balance the available controlled variant types rather than simply taking the first 30 corpus rows.

## Load tasks into Google Sheets

Open the backend Google Sheet and select the `Tasks` tab.

Before loading the real pilot, deactivate temporary debugging rows such as `test-001` by setting `active=FALSE` or move them to a different batch.

Import or paste the pilot CSV under the existing header. Do not edit `task_id` or `semantic_family_id` after annotation begins.

Expected task fields:

```text
task_id
semantic_family_id
kannada
roman
variant_type
source_type
source_id
source_author_id
batch_id
target_votes
active
```

For `pilot-v1`, confirm:

```text
batch_id = pilot-v1
target_votes = 2
active = TRUE
```

## Create 4–5 annotator links

Use pseudonymous IDs such as:

```text
KN001
KN002
KN003
KN004
KN005
```

Run `createAnnotator()` once for each person and send each person only their own generated URL.

Annotators should never receive:

- the Google Sheet;
- another annotator's URL;
- another annotator's decisions;
- synthetic/reference transliteration suggestions beyond the single candidate being judged;
- information about which examples are expected to pass or fail.

A short message to contributors is enough:

> You will see a Kannada sentence and the same content typed using English letters. Answer whether the meaning is preserved. If yes, also answer whether you would plausibly type Kannada that way. Skip anything you are unsure about. Please do not use search, transliteration tools, AI assistants, or another person while judging.

## Freeze the annotation wording during a batch

The pilot uses a versioned instruction identifier. Do not silently change the question wording during `pilot-v1`.

If the meaning or interpretation of the instructions changes, increment the instruction version and start a new batch so labels remain attributable to a specific protocol.

## Export annotations for analysis

After the pilot, export the `Annotations` tab as CSV and save it locally, for example:

```text
data/interim/romanbench/pilot-v1-annotations.csv
```

Then run:

```bash
make romanbench-pilot-analyze \
  PILOT_ANNOTATIONS=data/interim/romanbench/pilot-v1-annotations.csv
```

The analysis reports:

- annotation count;
- skip count and skip rate;
- number of unique tasks / semantic families observed;
- pairwise agreement for meaning labels;
- pairwise agreement for Roman-typing labels, computed only when meaning was `Yes`;
- count/rate of `Meaning=Yes, Typing=No` judgments;
- tasks with meaning disagreement;
- tasks with typing disagreement.

With `target_votes=2`, pairwise agreement is equivalent to the fraction of doubly annotated tasks on which the two annotators agree. The implementation also works if later batches use more than two annotators by computing agreement over all within-task annotator pairs.

## How to interpret the pilot

The pilot is primarily validating the **annotation procedure**, not establishing final leaderboard data.

Look for:

1. **Meaning agreement** — low agreement suggests ambiguous source/candidate pairs or unclear instructions.
2. **Roman-typing agreement** — disagreement is expected to be higher because typing conventions genuinely vary across speakers.
3. **Skip rate** — a high skip rate suggests difficult/unnatural source sentences or unclear Kannada.
4. **Meaning=Yes / Typing=No** — especially valuable examples: the candidate preserves meaning but is not a plausible everyday Roman-letter spelling for that annotator.
5. **Systematic disagreement by variant type** — useful for deciding which generator variants should be used, revised, or excluded in later construction.

Do not interpret agreement alone as benchmark correctness. Human votes are one component of provenance and quality control; final benchmark promotion still requires source review, contamination controls, split discipline, and release/version metadata.

## Before inviting a larger group

The pilot is ready to scale only after:

- the frontend and Apps Script versions are synchronized;
- a clean incognito end-to-end test succeeds;
- genuinely incorrect examples are present in demo/instructions;
- `Meaning=No` bypasses Question 2;
- 30-family task generation is deterministic and reproducible;
- 4–5 personal annotator links are tested;
- pilot analysis can be reproduced from an exported annotation CSV.
